# DNS & Public Hostname

FRP Auto Deploy treats the server's **Public IP** and optional **Public Hostname** as different concepts.

```text
Public IP
= primary infrastructure/control endpoint

Public Hostname
= optional user-facing alias for published services
```

## Example

```text
Public IP       203.0.113.10
Public Hostname fw.example.com
```

With a published SSH service on port `6000`, both can be used:

```bash
ssh -p 6000 user@fw.example.com
ssh -p 6000 user@203.0.113.10
```

For HTTP or HTTPS passthrough:

```text
http://fw.example.com:6001
https://fw.example.com:6002
```

## Configure the hostname

```bash
sudo frpctl set server hostname fw.example.com
```

Remove it with:

```bash
sudo frpctl unset server hostname
```

Setting the hostname does **not** change:

- CLIENT ID
- Service ID
- Public port reservations
- FRP control identity
- Project CA

## DNS remains your responsibility

FRP Auto Deploy does not automatically create DNS records or call Route53, Cloudflare DNS, or another DNS provider API.

Create the required A/AAAA record yourself so the hostname resolves to the public entry point for the FRP server or its firewall/NAT.

## HTTPS passthrough

FRP Auto Deploy does not terminate application HTTPS for published services. HTTPS is TCP passthrough, so the target web application's certificate must cover the hostname users connect to.

## Hairpin NAT

Clients on the same internal LAN may be unable to reach the public hostname through the firewall's public IP if the firewall does not support hairpin NAT. In that case, use hairpin NAT or split DNS.
