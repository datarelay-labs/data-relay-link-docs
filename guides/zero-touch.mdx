# Zero-Touch Enrollment

Zero-Touch is the recommended onboarding flow when the server operator wants to define the initial client profile and send the remote user one command to run.

## Generate a Zero-Touch SSH enrollment

On the FRP Auto Deploy server:

```bash
sudo frpctl create enrollment \
  --one-line \
  --ssh \
  --ssh-user aella \
  --label branch-a
```

Replace `aella` with an SSH account that already exists on the remote client.

FRP Auto Deploy does not create OS users, install or configure `sshd`, change passwords, create SSH keys, or modify `authorized_keys`.

## Treat the generated command as sensitive

The generated command contains a short-lived bootstrap credential. Send it through an appropriate private channel and do not paste it into public tickets, public chat rooms, analytics, or logs.

The ticket is designed to be short-lived, first-machine bound, and single-use after successful enrollment.

## Stable v2.1.2 behavior

The stable v2.1.2 flow uses the transitional `zt1` bootstrap package generated by the server. Always run the exact command printed by `frpctl` rather than reconstructing it manually.

## Short URL development path

The 2.1.3 development tree adds an optional operator-managed public bootstrap hostname that can produce a shorter command of the form:

```bash
curl -fsSL https://bootstrap.example.com/i/<opaque-ticket> | sudo bash
```

This requires operator-managed DNS, publicly trusted TLS, and a reverse proxy. It is separate from the normal published-service hostname. Do not assume this short-URL flow is available on a v2.1.2 stable server.

## Verify enrollment

Back on the server:

```bash
sudo frpctl show clients
sudo frpctl show enrollments
```

A successfully enrolled client gets a persistent CLIENT ID. Normal service edits, supported updates, and reboots do not require a fresh enrollment.

## Revoke vs purge

```bash
sudo frpctl revoke enrollment <ID>
sudo frpctl purge enrollment <ID>
```

`revoke` blocks an active credential. `purge` removes terminal enrollment metadata. They are intentionally different lifecycle operations.
