# Quick Start

This guide uses the current stable release, **v2.1.2**, and takes you from an empty Linux server to a working remote SSH connection.

## Before you start

You need:

- one supported Linux/systemd server that remote clients can reach
- one Linux/systemd client to enroll
- an SSH account that already exists on the client
- the required firewall/NAT rules for the server deployment

For the default Direct deployment, the usual public inbound TCP requirements are:

```text
443         FRP control
6099        Enrollment / management HTTPS
6000-6098   Published services
```

<Warning>
  FRP Auto Deploy does not automatically change an external firewall, cloud security group, NAT rule, UFW, firewalld, or iptables policy.
</Warning>

## 1. Install the server

On the Linux server:

```bash
curl -fsSL \
  https://raw.githubusercontent.com/datarelay-labs/frp-auto-deploy/v2.1.2/dist/bootstrap-server.sh \
  | sudo bash
```

The interactive installer asks for the public endpoint, optional published-service hostname, internal IP, deployment mode, and port settings.

If the server is behind a firewall/NAT device, read [Firewall & NAT](/deployment/firewall-nat) before accepting port assumptions.

## 2. Verify the server

```bash
sudo frpctl show version
sudo frpctl show status
sudo frpctl doctor
```

`doctor` is read-only and is the preferred first diagnostic command.

<Check>
  Continue only after the expected server services are active and `doctor` does not report a blocking configuration error.
</Check>

## 3. Create a Zero-Touch SSH enrollment

On the server:

```bash
sudo frpctl create enrollment \
  --one-line \
  --ssh \
  --ssh-user aella \
  --label branch-a
```

Replace `aella` with an SSH user that **already exists on the remote client**.

FRP Auto Deploy does not create OS users, install or configure an SSH server, change passwords, or manage SSH keys.

The server prints a one-time bootstrap command. Treat the complete command as short-lived sensitive material and send it to the remote operator through an appropriate private channel.

## 4. Run the generated command on the client

On the remote Linux client, run the **exact command printed by the server** once.

After installation, verify locally:

```bash
sudo frpctl show status
sudo frpctl show services
sudo frpctl show info
sudo frpctl doctor
```

<Check>
  The client should show the enrolled service and a healthy FRP client state.
</Check>

## 5. Confirm registration on the server

Back on the server:

```bash
sudo frpctl show clients
sudo frpctl show enrollments
```

The enrolled machine receives a persistent CLIENT ID and its SSH service receives an assigned public service port.

For more detail:

```bash
sudo frpctl show client <CLIENT-ID>
sudo frpctl show client <CLIENT-ID> services
```

## 6. Connect over SSH

```bash
ssh -p <public-port> aella@<FRP-server-public-IP>
```

If you configured an optional published-service hostname:

```bash
ssh -p <public-port> aella@fw.example.com
```

The server public IP remains the infrastructure fallback.

## Success checklist

You are finished when all of the following are true:

- `show clients` lists the client with a CLIENT ID
- the SSH service has a public service port
- the client reports healthy state
- the server's published service port is reachable through the external firewall/NAT
- `ssh -p <public-port> ...` reaches the intended client SSH service

## If it does not work

Start with [Troubleshooting](/troubleshooting/overview) and `frpctl doctor` on both server and client. Avoid manually editing registry, identity, or generated FRP files as a first response.
